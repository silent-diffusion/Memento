# Memento — Architecture

This document fixes the technical decisions for the Memento Windows application. `PRODUCT-SPEC.md` says what the app must do; `../design/DESIGN.md` says how it looks; this document says how it is built. Builders follow it; changes to it are deliberate and reviewed.

## 1. Platform and stack

| Concern | Decision | Why |
|---|---|---|
| Target OS | Windows 11 (primary). Windows 10 version 2004+ is tolerated where it costs nothing. x64 only. | Per-process audio capture needs Windows 10 2004+; the product owner runs Windows 11. |
| Host | .NET 8, C#, WPF window hosting a single **WebView2** control. Self-contained publish (`win-x64`, runtime bundled). | Best-supported access to WASAPI, Media Foundation, Windows OCR and GPU inference libraries; no runtime install for end users. |
| UI | TypeScript + **Preact** + Vite, static assets embedded in the app and served through a WebView2 virtual host (`https://app.memento/`). Styling comes from `design/tokens.css` and the markup in `design/renders/`. Fonts (Manrope, JetBrains Mono; both OFL) are bundled, never fetched. | The design handoff is HTML/CSS; rebuilding it in XAML would lose fidelity. |
| Storage | One folder per recording project holding JSON and media files. A SQLite index (`library.db`, with FTS5) that can always be rebuilt from the project folders. | Local-first, user-owned, inspectable, survives index corruption. |
| Audio capture | WASAPI shared-mode, event-driven. NAudio 2.4 (the last .NET 8 release) for device and session enumeration; **our own capture loop** (hand-written COM interop, about 150 lines, no CsWin32) for every source so each packet carries its QPC and device-position timestamps. Per-process loopback via `ActivateAudioInterfaceAsync` + `AUDIOCLIENT_ACTIVATION_TYPE_PROCESS_LOOPBACK` with `INCLUDE_TARGET_PROCESS_TREE`. Endpoint loopback delivers **no packets during silence**, so the writer inserts clock-timed silence for it; process loopback streams zeros continuously and is preferred when the user picks apps. | Verified in the 2026-10 spikes (ENGINE-NOTES.md §C). |
| Audio encode/decode | Windows **Media Foundation** built-in codecs: FLAC (bit-exact round trip verified), MP3, AAC (m4a), WAV. No bundled ffmpeg, no libFLAC. The FLAC output type is obtained from the FLAC MFT (`SetInputType` → `GetOutputAvailableType(0)`), input is int16/int24 PCM (float is converted first), and FLAC is encoded **only from finished WAV tracks** because the MF FLAC sink writes nothing until it finalizes. | Zero native dependencies (ENGINE-NOTES.md §A). |
| Transcription | **Whisper.net** 1.9 (whisper.cpp) with runtime order `[Vulkan, Cpu]`; **no CUDA** (it brings no speed gain on the reference GPU, needs ~690 MB of extra DLLs and aborts the process when it fails to load). Runs in a **separate worker process** so a native assert cannot take down the app and VRAM is released cleanly. Default model `large-v3-turbo` on a GPU with ≥ 2.5 GB free VRAM, `small` on CPU; the discrete GPU is chosen explicitly; a short punctuated prompt is always passed; DTW timestamps are never enabled; a coverage check flags stretches of speech energy with no transcript. The VC++ runtime DLLs are shipped app-locally. Models are downloaded on first use, never bundled. | Measured RTF 0.038 for large-v3-turbo on Vulkan vs 1.03 on CPU (ENGINE-NOTES.md §D). |
| Speaker identification | **sherpa-onnx** 1.13 offline diarization: pyannote `segmentation-3.0` + `nemo_en_titanet_small` embeddings, clustering by threshold 0.8 (pure voices; ENGINE-NOTES.md §L), `ComputeConfidence` on; run per track; the host groups the voices of all tracks to the recording's own or Settings' expected count (never splitting) and names them (§6). | Separated two readers exactly and kept one reader whole; RTF 0.10 on CPU; 22 MB native footprint (ENGINE-NOTES.md §E). |
| OCR (agenda photos and scanned PDFs) | **Windows.Media.Ocr** by default: input upscaled so body text is ≥ 24 px, line boxes built from word boxes, results always shown for review (no confidence is available). **Tesseract 5.5** (2.0; TesseractOCR binding, Apache-2.0) as the installable alternative, chosen in Settings › Documents › Agenda photos and scans once its English language data (`tesseract-eng`, tessdata_fast, 4 MB) is installed, and the fallback when the OCR language is not installed in Windows. Tesseract runs in **Memento.Worker** (an `ocr` job that stays loaded for the passes of one import), never in the app: the host decodes the image with Windows' decoders, evens out the paper (per-tile background division), upscales to a 32 px median word and straightens it with the same passes as Windows OCR (`OcrPasses`), and sends raw gray pixels; the worker answers with words, boxes, per-word confidence and the text angle. A word under 0.6 confidence marks its item uncertain, beside the misread-character checks both engines share. | Built-in is free and local; the alternative satisfies the "open-source, downloadable, managed in Settings" rule, and out of process a native failure cannot reach a recording (ENGINE-NOTES.md §F, §P). |
| Agenda parsers | DocumentFormat.OpenXml (docx, xlsx), PdfPig (pdf), built-in CSV/Markdown/plain text. | All MIT/Apache, pure managed. |
| Document export | DOCX via DocumentFormat.OpenXml; PDF by rendering the same HTML the viewer shows through WebView2 `PrintToPdfAsync`; Markdown by serializer. | The preview is the contract: PDF comes from the exact preview HTML. |
| External AI | `IAiProvider` abstraction with Anthropic (Messages API) and OpenAI implementations. Off by default. | Spec requirement; extensible to more providers. |
| Secrets | API keys encrypted with Windows DPAPI (user scope) in `%LOCALAPPDATA%\Memento\secrets.bin`. Never in settings.json, logs, exports or project folders. | Keys must never be echoed or leak into a shared project. |
| Logging | Serilog, rolling files in `%LOCALAPPDATA%\Memento\logs\`. Logs may contain file paths and engine diagnostics; they must never contain transcript text, document text, participant names or keys. | Diagnosable without leaking content. |
| Installer and updates | **Velopack**: `Setup.exe` one-click install per user, delta updates from GitHub Releases, no admin rights. WebView2 Evergreen runtime bootstrapped if missing. Unsigned for now. The Velopack pack id is `MementoApp` (installer `MementoApp-win-Setup.exe`, installed to `%LOCALAPPDATA%\MementoApp`) because Velopack replaces or deletes its whole install folder, and the data root is `%LOCALAPPDATA%\Memento`. The id is permanent. From 1.0.0 (the first public release; 0.5.0 was folded into it) the app checks the GitHub releases feed (`UpdateService` over Velopack's `UpdateManager` and `GithubSource`) once the page is ready and every 24 h, never while a recording or processing stage runs, downloads in the background and installs only on "Restart to update" or at the next start; pre-releases count only for pre-release builds; "Install updates automatically" (on by default) controls the automatic checks. Releases from 0.5.0 on are full GitHub releases (a version with a suffix stays a pre-release). The hidden `--update-feed` test switch takes only `off`, a local folder or an address on this PC, and in Release builds only `https:` (`UpdatePolicy.IsAllowedFeed`). | Matches "download and install with one click". |
| CI | GitHub Actions on `windows-latest`: build, test, lint on every PR; tag `v*` publishes a release with `Setup.exe` and the Velopack update feed. | Every release is reproducible from a tag. |
| Versioning | SemVer. `0.y.z` until the first public release `1.0.0`. | |

**Engine philosophy.** Every engine (transcription, diarization, OCR, and later anything else) is selected in Settings from a catalog of built-in and downloadable open-source options. A single **Model manager** in Core handles download, SHA-256 verification, storage under `%LOCALAPPDATA%\Memento\models\<engine>\`, removal, and reporting installed state and size. Downloads come only from the publishing hosts (huggingface.co, github.com and their CDN hosts, checked again after redirects); a resumed download is appended only when its `Content-Range` matches; each installed file gets a `<file>.verified.json` hash stamp that must match the catalog, the size and the file time before the file is used, and a file without one is hashed once in the background (security audit 2026-10-07). New engines register with the catalog; they do not add UI outside Settings.

**Not in 1.0:** video capture (screen, window, camera). The project schema reserved fields for it so adding it did not change how recordings are stored; 2.0 adds it as described in §5.x.

Dependency direction: `App → Core ← Audio, Transcription, Documents, AI`. Feature projects depend on Core's interfaces; Core never references them. App composes everything with `Microsoft.Extensions.DependencyInjection` and `Microsoft.Extensions.Hosting`.

## 3. Host ↔ UI bridge

One channel: WebView2 `postMessage` in both directions, JSON only.

- **Request/response** (UI → host): `{ "id": 17, "method": "library.list", "params": { ... } }` answered by `{ "id": 17, "result": { ... } }` or `{ "id": 17, "error": { "code": "...", "message": "...", "detail": "..." } }`.
- **Events** (host → UI): `{ "event": "recording.levels", "payload": { ... } }`. High-rate events (levels, playhead, progress) are throttled on the host to ≤ 30 per second.
- Method names are `area.verb` (`library.list`, `recording.start`, `transcript.editSegment`, `settings.get`, `export.run`). Every method and event has a C# record in `Memento.Core/Bridge/Contracts/` and a matching TypeScript type in `ui/src/bridge/types.ts`. Keep the two in sync by hand and cover each with a serialization test.
- The host validates every incoming message; the UI never receives file-system paths it did not ask for and never receives API keys in any form (only "a key is saved" booleans).
- The page never names a file for the host to read: files come from the host's own picker or a drop the host recorded, and a `path` in a request is refused. File names inside `project.json` are untrusted (a project folder can be copied in) and are resolved only inside the project folder; junctions and symbolic links are never followed when walking, deleting or moving the library. The worker is stopped as hung after 30 minutes without a protocol line. See `docs/SECURITY.md`.
- Dialogs that need the OS (file pickers, folder pickers, "open Windows settings") are host methods.

The UI is a single page. Navigation is in-page (hub and spoke per the design) and the Library's scroll position, filters and search are kept in UI state when a spoke opens.

## 4. Data on disk

Default library location: `%LOCALAPPDATA%\Memento\Library`. **Not** Documents, because on Windows 11 Documents is often synced to OneDrive, which would silently upload recordings. The location is changeable in Settings; moving the library is a copy-then-verify-then-delete operation with progress. The default library is created on first run; a library elsewhere that is missing at launch (a removable drive that is not connected, a renamed folder) is reported (`library.unavailable`) and never re-created empty, and recording is refused until it is back; it opens by itself once it is.

```
Library/
├── library.db                       SQLite index: recordings, people, FTS over titles/transcripts/people, each row's folder. Rebuildable.
├── folders.json                     2.1: the Library's folder tree (paths such as "Clients/Acme"), so empty folders survive; schemaVersion 1.
├── voices/known.json                2.0, opt-in: known voices (signatures under confirmed names, never audio). Not rebuildable; Settings › Speakers deletes it.
└── projects/
    └── 20261006-100000-k3f9ab/      id = local date-time + 6 random base32 chars
        ├── project.json             manifest (schema v6): title, type, created (UTC + local offset), details, participants, agenda, tags, tracks[], videoTracks[], segments[], folder, audioRemoved, status, integrity
        ├── tracks/
        │   ├── mic.flac             one file per source; .wav while recording, encoded at finalize
        │   ├── system.flac
        │   └── screen.mp4           2.0: a video track, fragmented MP4 as recorded (camera.mp4, screen.part2.mp4 after an encoder change)
        ├── mix.flac                 playback/export mixdown, written at finalize
        ├── peaks.json               waveform peaks for the UI
        ├── transcript.json          segments, words, confidences, speakers, language, engine metadata
        ├── voices.json              what the last speaker pass heard: turns and voice embeddings per track, and the lines each voice won (never exported)
        ├── annotations.json         chapters, highlights, topics, notes (with origin: user / local / ai)
        ├── documents/
        │   └── <docid>.json         block content + generation record (template, style, provider, inputs, time)
        ├── templates/ styles/       project-local overrides, if any (global ones live under %LOCALAPPDATA%\Memento)
        ├── attachments/             imported agenda files and other attachments, original bytes
        ├── versions/                previous versions when history is on: <file>.<utc-stamp>.json
        ├── history.jsonl            append-only processing log (one JSON object per line)
        └── recording.state.json     exists only while a recording is in progress; drives crash recovery
```

Rules:
- `project.json` carries `schemaVersion`. Readers accept older versions and migrate forward; writers always write the current version. Unknown fields are preserved on round-trip. Schema v2 (0.4.0) adds the typed `attachments` index (id, name, file, size, SHA-256, added, kind `agenda` | `file`, content type); the v1 → v2 step keeps every readable entry and drops damaged ones. Schema v3 (after 1.2.0) adds `details.whoSpoke`, the recording's own speaker count and names; the v2 → v3 step writes an empty one and keeps what is readable of a damaged one. Schema v4 (2.0) types `videoTracks` and adds `videoPip` and `videoRemoved` (§5.x); the v3 → v4 step keeps readable video entries and drops damaged ones. Schema v5 (2.1) adds `folder` (the Library folder, a path such as `Clients/Acme`, `null` at the root) and `audioRemoved`; the v4 → v5 step writes `folder: null` and sets an unreadable folder to the root.
- **Folders (2.1)** are data, never directories: a recording's folder is `project.json`'s `folder`, and the tree is `folders.json` together with every folder a manifest names (`FolderService`, `FolderStore`, `FolderPaths`). Creating, renaming, moving or deleting a folder, or filing a recording, rewrites manifests (atomically, each through `ProjectCatalog` so the index row follows) and then `folders.json`; no recording file moves, so an interrupted rename leaves every recording in a folder that is still shown. Deleting a folder files what it held in its parent. Names are 1–80 characters without `/`, `\` or control characters, compared without case, eight levels at most. `library.db` (schema 4) caches each row's `folder` and `audioRemoved`, so `library.list { folder }` filters in SQL.
- **Dates (2.1)**: `settings.general.dateFormat` (`Memento.Core.Formatting.DateFormats`: `yearMonthDay` default, `dayMonthYear`, `monthDayYear`, `iso`, `windows`) is how every full date is written: the host's default title ("Untitled meeting · 2026 February 16", `RecordingCoordinator`), the documents' meta line and running header (`MetaLine.DateFormat`, kept in step by the app's `DateFormatSync`), and the page's own dates (`ui/src/format/dates.ts`). Stored timestamps are unchanged (ISO 8601).
- Writes are atomic: write to `<name>.tmp`, flush, then `File.Move(overwrite: true)`. The replace (`Memento.Core.Storage.AtomicReplace`) uses a POSIX-semantics rename (`SetFileInformationByHandle`, `FileRenameInfoEx`) so a reader holding the file with `FILE_SHARE_DELETE` neither blocks the write nor sees a torn file (it keeps the old one until it closes); on FAT/exFAT, some network shares and older Windows it falls back to `File.Move`, and either way a lock is retried for about 10 s of waits with jitter before the write fails (2 s until 2.1.x: a virus scanner reading a just-written file on a loaded machine outlasted it) (the waits asked for are counted, not the clock, so a saturated machine that wakes the retry loop late still gets every try).
- Original tracks are never modified after finalize. Storage optimisation (downmix, lossy) writes new files and records the operation and the resulting hashes in `history.jsonl`; the user opts in.
- `integrity` in the manifest lists SHA-256 for every track and the mix, computed at finalize. Exports write a `manifest.json` beside the files with the same hashes.
- Timestamps are ISO 8601 with offset; durations are milliseconds; transcript times are seconds as decimals.

## 5. Recording pipeline

1. **Sources.** Enumerate: capture endpoints (microphones), render endpoints for system loopback, running processes with audio sessions for per-app loopback. Each enabled source becomes a **track** with its own capture client, ring buffer and writer.
2. **Capture.** WASAPI shared mode, event-driven, through one shared capture loop that records each packet's QPC and device-position timestamps. The endpoint mix format (float32 48 kHz on current Windows) is kept per track; resampling happens only at mixdown, onto the highest track rate (a 44.1 kHz and a 48 kHz track stay within 2 ms of each other over minutes, ENGINE-NOTES.md §K), and the player follows the mix with `<audio>`'s own clock, which matches the audio within milliseconds for FLAC and within 25–44 ms for Memento's MP3 and AAC. Tracks share a session start time taken from QPC; each track's first packet is stamped so start-up latency (100–350 ms, different per stream) is corrected. Endpoint loopback produces no packets while nothing plays, so the writer inserts clock-timed silence to keep that track aligned. Drift (frames written vs clock) is measured and logged at every checkpoint.
3. **Writing.** Each track streams to `tracks/<source>.wav` as **int24 PCM** (float32 converted on the write path; it is what the FLAC encoder takes and saves 25% disk). Every **checkpoint** (30 s default): flush all writers to disk (`FlushFileBuffers`), patch the RIFF size fields, flush again, write `recording.state.json` (session start, tracks, bytes written, last checkpoint time). Writers also flush their managed buffer once per second so a process crash loses under 200 ms. Classic RIFF stops at 4 GiB, so a track rolls over to `tracks/<source>.part2.wav` at 3.5 GiB; finalize joins the parts into one FLAC. RAM use is bounded by the ring buffers.
4. **Pause/resume** stops writing but keeps capture clients alive; the gap is recorded in the manifest so transcript timings stay continuous.
5. **Source change mid-recording** starts or stops one track only. A lost device marks the track ended at that time and raises the toast; other tracks continue.
6. **Stop / finalize.** Close writers, encode each track to FLAC (always lossless; see the storage format options below), write `mix.flac` and `peaks.json`, hash, update the manifest, delete `recording.state.json`, append `history.jsonl`, index in SQLite, then queue processing stages. The MF FLAC sink buffers the whole encode in `%TEMP%` and writes the output only at the end, so finalize checks free space there first and, if encoding fails for any reason, keeps the WAV tracks and reports it rather than leaving the project without media. **Even out source levels** (after 2.0.0-beta.1, Settings › Recording › Storage, `recording.storage.evenLevels`, on by default): before the mix is built each capture WAV's speech level is measured (`TrackLevels`, `SpeechLevel`), and a track more than 3 dB under the loudest is lifted to it in the mix (`MixLevels`: at most +24 dB, never lowered; a track without speech keeps its level), through `MixInput.Gain`, with the mixer's soft limiter as before. Only `mix.flac` changes; the gains go into `project.json` (`mix.evenLevels`) and the `stored` History line. Existing recordings: `project.rebuildMix` (Review › More › Reprocess) writes `mixRebuild` into the manifest and queues the on-request `mix` stage (`MixStage`, order 90), which mixes the stored tracks again with or without evened levels into `mix.rebuilt.flac` (verified, hashed) and `mix.rebuilt.peaks.json` via `ITrackFinalizer.RebuildMixAsync`, moves them over `mix.flac` and `peaks.json`, records the new hash and gains, writes History, and queues `optimize` again when the old mix was a smaller format and Settings still asks for one. Undone only by rebuilding again (as recorded). Once it has run, `mixUrl` and `peaksUrl` carry `?v=<hash>` so WebView2 does not play a cached copy.
7. **Disk watch.** Free space is sampled every 5 s. Below the warning threshold (10 GB default) a banner appears and transcription pauses; if a write fails for lack of space the recording stops cleanly, everything written is kept, and the exact stop time is reported.
8. **Recovery.** On launch, any project with `recording.state.json` is repaired (RIFF headers rewritten from file length), finalized, and offered in the recovery dialog. An export that was still running when Memento closed (journalled in `%LOCALAPPDATA%\Memento\exports-running.json`) has the files it wrote removed, as a failed export would, and the recording's History says so. Installed models are checked against their SHA-256 before a stage uses them; a damaged file is set aside and downloaded again.
9. **Live transcript** (2.0; Settings › Transcription › Live transcript while recording, off by default, which is `transcription.timing: during`). `LiveTranscriptService` (Memento.Transcription) looks at the session every 500 ms. Each 10 s window of the recording timeline (pauses excluded) is read once every open track's samples on disk cover it: `LiveMixReader` opens the growing capture WAVs read-only with full sharing, behind the writers' once-a-second flush, follows `.partN.wav` rollovers, mixes each track to mono, box-filters it to 16 kHz, brings each track's speech in the window to −20 dBFS (`LoudnessNormalizer`, after 2.0.0-beta.1, so a quiet microphone is not buried under loud system audio; a track without speech in the window keeps its level), places it by its start offset and scales the sum only if it would clip. Nothing touches the capture or writer threads. A silent window (below −50 dBFS after that) is skipped; a draft that falls more than one window behind skips to the latest complete one (`LiveWindows`). One worker job (`live`) keeps the model loaded and answers each `audio` line with a `heard` line: the Small model, Base when Small is missing, never Turbo, Medium or Large; on the processor with a quarter of the threads (1–4) at below-normal priority, and on the graphics card only when Settings allows it (`transcription.liveOnGpu`) and the card is free. Windows are heard whole, each without the previous one's text, with the encoder's audio context cut to 12.8 s and no retries at higher temperatures (no packing or alignment: the full pass does that, unchanged). The lines go to the page as `recording.liveTranscript` with a state, the engine and a §17 note, are kept in memory only (never written to the project; the optional `live.jsonl` sidecar was not built, so recovery has nothing to delete), are discarded when the session ends, and the unchanged full pass after Stop replaces them. It never competes with a full pass: while a heavy stage runs (`ProcessingOrchestrator.IsHeavyStageRunning`) it stops its worker and says why; it never queues for the card (`WorkerClient.TryOpenAsync`); and it ends a card session the moment another job waits for the card (`WorkerClient.GpuWanted`), staying on the processor for the rest of that session. Measurements: ENGINE-NOTES.md §O.

10. **Resume a stopped recording** (2.1, `recording.resumeStopped`, `RecordingCoordinator.ResumeStoppedAsync`). A recording started today that is saved and still has its tracks (`ResumePolicy`) takes another **segment**: a new engine session in the same project folder whose plan reserves every track id the project uses (`RecordingPlan.ReservedTrackIds`; WASAPI `AudioRecordingOptions.ReservedStems`; video `VideoRecording.ReservedTrackIds`), so it writes `tracks/mic-2.wav`, `tracks/screen-2.mp4` and never opens a finalized, read-only file. Its time 0 is placed at the recorded time so far (`SegmentOffsetMs`): segments sit end to end and the real time between Stop and Resume becomes a `ProjectPause` at that offset (shown as a pause, never recorded silence). The capture path is untouched: the offset is applied only where the coordinator writes the manifest, `recording.state.json` and highlights. Processing of the recording is cancelled at resume. `project.json` **schema v6** adds `segments[]` (`ProjectSegment`: index, startedAt, offsetMs, durationMs, gapMs, endedAt; the v5 → v6 step writes one) and `segment` on each later track and video track. `recording.state.json` gains `segment` and `segmentOffsetMs` and lists only the segment's tracks, already on the recording timeline, so checkpoints and **recovery work per segment**: recovery keeps the earlier segments' hashed tracks as they are and repairs only the state file's. Finalize (`ProjectFinalizationService`) encodes only the tracks without a hash, then mixes every track of every segment again (`ITrackFinalizer.RebuildMixAsync` into `mix.segments.*`, moved over the mix and `peaks.json`), keeps the earlier hashes, and queues every stage that had run again over the **whole recording** (a pass over only the new segment is not available; History says so; `Processing.Retranscribe` keeps the earlier transcript as a version). `library.db` schema 5 stores `resumedAt` for the Library row. No undo; Stop ends a segment like any session.

Storage format options (Settings › Recording): **Lossless FLAC** (default), or a smaller format after processing: AAC or MP3 at a chosen bitrate, optional mono downmix, optional "keep only the mix". Finalize always stores lossless FLAC; a lossy choice is applied by a separate `optimize` stage that the orchestrator runs after every other processing stage, which writes the lossy files, verifies that they decode, updates the manifest hashes and `history.jsonl`, and only then removes the FLAC files it replaced. The transcript is always produced from the lossless files before any lossy conversion. **Keep only the mix** (2.0, off by default) also runs in the `optimize` stage, after the smaller format when one is chosen (then only the mix is converted): the mix is checked against its SHA-256 in `project.json`, the manifest records `mixOnly { at, trackIds, bytesFreed }` and drops the tracks' hashes (an optional field within schema 3), and only then are the separate track files deleted; a missing or mismatched mix keeps every track and History says why. Such a recording is transcribed again from its mix as one track; speakers cannot be identified per track again and tracks cannot be exported. Settings › Storage and history shows what separate tracks use (`library.usage`) and removes them from existing recordings after a confirmation (`storage.keepOnlyMix`, a reclaim job). `settings.json` schema 2 starts keep-only-the-mix and the live transcript off when they were saved by 1.x, where they did nothing.

### 5.x Video (2.0, from the spike in ENGINE-NOTES.md §M)

Video is one more synchronized track, never the recording itself (DESIGN.md §18): it can fail, pause or be removed on its own while audio continues, and it is never transcribed, analysed or sent anywhere. The capture library is `src/Memento.Video` (net8.0-windows10.0.19041.0, the app's target; Direct3D 11 and Media Foundation through Vortice, Windows.Graphics.Capture through the Windows SDK projection). Core reaches it through two seams it defines, `IVideoCapture` (sources, thumbnails, one `IVideoTrackRecorder` per track) and `IVideoFiles` (repair, join, export files), implemented by `Memento.Video.Hosting` (`MediaFoundationVideoCapture`, `MediaFoundationVideoFiles`, registered by `AddMementoVideo`); without them Core uses stand-ins that list nothing and refuse to start (`video.unavailable`). The bridge contract is BRIDGE.md "Video (2.0)".

1. **Sources** (`IVideoSource`, listed by `VideoSourceEnumerator` without opening anything). Displays and windows through **Windows.Graphics.Capture** (`GraphicsCaptureSource`): one capture item per display (`HMONITOR`, named by the GDI device name, "Display 1" = the primary, the others left to right) or window (`HWND`); the yellow border is turned off where Windows allows it (Windows 11: `IGraphicsCaptureSession3.IsBorderRequired`; Memento's own Recording screen says what is captured); the mouse pointer follows Settings. Cameras through the **Media Foundation source reader** (`CameraCaptureSource`) on the same device, with advanced video processing so MJPG cameras are decoded and every frame arrives as NV12 on the GPU. Cameras Media Foundation does not list (the OBS Virtual Camera, NDI, Snap Camera, DirectShow-only capture cards: video input filters registered under `CLSID_VideoInputDeviceCategory`) through **DirectShow** (ENGINE-NOTES.md §R): the list merges both (`CameraListMerger`; a camera both see is kept once, from Media Foundation; `VideoSource.backend` says which, ids `camera:dshow:…`), and `DirectShowCameraSource` runs a filter graph (device filter → qedit sample grabber → null renderer, hand-written COM interop, all calls in the MTA) whose streaming thread only copies each picture into a bounded three-buffer queue (dropped and counted when full); a conversion thread turns YUY2, UYVY, NV12, I420, YV12 and RGB into NV12 on the processor (MJPG is decoded by DirectShow's decoder in the graph) and uploads it into the source's texture, so pacing and encoding are the same as for any camera. A virtual camera's filter keeps running when its app stops, so the OBS Virtual Camera is watched through the header of the shared-memory queue OBS writes: not started → refused, stopped → the track ends (`sourceLost`). Third-party DirectShow filters run inside Memento's process (a Media Foundation camera runs in Windows' Frame Server service), so cameras held for thumbnails are closed when the app closes. Windows that ask Windows to keep them out of captures (display affinity, e.g. protected players) are refused as protected content instead of being recorded black; Memento's own windows are listed but excluded.
2. **One Direct3D 11 device per track** (`VideoDevice`, multithread-protected) on the adapter that drives the captured display (`VideoDevice.AdapterForDisplay`; a camera on the first adapter), shared by capture, conversion and the hardware encoder, so a picture never leaves the GPU; a source switched to a display on another card is copied across by Windows. A source keeps only its **latest picture** (a GPU copy into a texture it owns; the frame pool's buffers go straight back to Windows).
3. **Pacing** (`FramePacer`, a dedicated thread at above-normal priority, below the audio threads' MMCSS priority). Slot *k* of a track is due at `origin + k / fps` on the QPC clock the audio tracks use (`QpcClock`; a captured frame's `SystemRelativeTime` is QPC time, the moment it is shown). At each slot the latest picture is converted on the GPU's video processor to NV12 at the track's size (letterboxed when a window's shape differs) and handed to the encoder. A still screen repeats its last picture (nearly free in H.264); a slot the thread reaches more than a frame late, or one the encoder has no free surface for, is **dropped and counted**, never waited for. A source with no pictures (a minimised window, a disconnected display) leaves a gap: the frame before it simply lasts longer. A recording pause rebases the pacer so paused time is left out of the video exactly as it is left out of the audio.
4. **Encoding** (`Mp4TrackWriter`): the Media Foundation sink writer, H.264 High profile, peak-constrained VBR at the quality's mean (Smaller 6, Balanced 12, Best 20 Mb/s at 1440p30, scaled by pixel rate to the power 0.75), key frame every 2 s, no B-frames, low-latency mode, from a bounded pool of 8 NV12 surfaces (`IMFVideoSampleAllocatorEx`). The hardware encoder of the device's adapter (NVENC, Quick Sync, VCN) when Settings' switch is on and it opens, else Microsoft's software encoder. Media Foundation's MP4 sinks keep **sample durations, not time stamps**, so the writer holds each frame until the next one arrives and gives it the real duration; gaps and drops therefore stay on the timeline. The file has no `tfdt`: it starts at 0, and the manifest's `startOffsetMs` places it.
5. **Files and crash safety.** Each track is written as **fragmented MP4** (`MF_TRANSCODE_CONTAINERTYPE = FMPEG4`): `tracks/<id>.mp4` gets its header first and then a fragment of about 10 frames (0.33 s at 30 fps); a clean stop appends an `mfra` index. At every recording checkpoint the file is flushed (`FlushFileBuffers` through a second handle; the sink's byte stream is opened with write sharing) and the track's `VideoTrackCheckpoint` goes into `recording.state.json` (`videoTracks[]`). A killed process keeps every complete fragment; recovery (`VideoRecovery`) cuts an incomplete trailing fragment off, if any, and remuxes the file without decoding (`Mp4Remuxer`) into an ordinary MP4. WebView2 plays and seeks both the fragmented file (with or without `mfra`) and the remuxed one to the frame, so a clean stop needs no finalize step for playback; the Video stage (DESIGN.md §18.7) only joins parts and composes the inset for export.
6. **Failures** fail the video track first and alone (DESIGN.md §18.6), raised as `VideoCaptureSession.Problem` with the §17 sentence and the time: a hardware encoder that fails mid-recording is replaced by the software encoder in a new part (`tracks/<id>.part2.mp4`); a full disk or an unwritable folder ends the video track; a closed window or an unplugged camera ends its track; a disconnected display makes the track wait (the user can switch it to another display, which continues the same track, letterboxed); camera privacy off, a camera held by another app (named from Windows' capability access records) and capture blocked by privacy settings each have their own error.
7. **Manifest.** Video tracks go into `project.json`'s `videoTracks[]` (reserved since schema v1 and preserved untouched by every 1.x reader, which mixes, transcribes and hashes every entry of `tracks[]` as audio), each with `kind: "video"`, `role` (`screen` | `camera`), source, file and parts with their start offsets, size, frame rate, quality, bitrate, encoder, `startOffsetMs`, `durationMs`, frames written and dropped, and an end reason (`VideoTrack`). `hasVideo` becomes true. The schema bump to **v4** adds the typed `videoTracks` (the v3 → v4 step keeps readable entries and drops damaged ones, as v2 did for attachments) and `integrity` hashes for the video files.
8. **Picture-in-picture**: screen and camera are always recorded as **two tracks**; the inset is drawn by Review's player (where it can be moved, §18.3) and composed only when an export asks for one file (§18.4). A second hardware encoder session for the camera costs 4–5 % of the encode engine and keeps the camera at its own resolution and frame rate (ENGINE-NOTES.md §M.5).
9. **Sync.** A video track is on the QPC timeline by construction: over 22 minutes its flashes stayed one frame after their scheduled instants with −1.7 ppm drift. What moves relative to it is an audio device clock (a microphone measured −23 ppm here, −93 ppm in H1); the planned audio drift correction, or storing the checkpoint drift readings for the player, closes that (ENGINE-NOTES.md §M.4).
10. **Orchestration** (`RecordingCoordinator` with `VideoRecording`, Core). `recording.start` takes video source ids beside the audio ones (one per role: the first display or window is the `screen` track, the first camera the `camera` track; at least one audio source is still required). The audio session starts first; each video track then starts with `TimelineOriginQpc` = the session's QPC start (`IRecordingSession.TimelineOriginQpc`, the WASAPI session's `StartedAtQpc`) plus the paused time so far, so its `startOffsetMs` is where its first frame sits on the audio timeline (0.6 s after the start on the reference laptop: opening the device and the encoder). A source that cannot start is reported (`recording.videoProblem` with its code and the track's state) and the audio records anyway; a camera another app holds is tried every 2 s and starts by itself once free. Pause and resume reach the tracks after the audio; every audio checkpoint flushes each video file (`FlushFileBuffers`) and writes its `VideoTrackCheckpoint` into `recording.state.json` before the state file is replaced; `recording.setVideoSource` switches a track's source (it continues, letterboxed), ends it (`endReason: disabled`) or starts a new one (`screen-2` in the manifest) after it ended; `recording.setVideoQuality` continues the tracks in a new part at another bitrate; `recording.setPip` records the inset's changes with their times (`videoPip[]`). Every track problem (`VideoCaptureSession.Problem`, raised off the pacing thread) becomes `recording.videoProblem` with one of the closed list of codes (`VideoProblemCodes`: four are states, such as a minimised window, and seven are the video error codes), the source and the other party, and the §18.6 sentence as fallback; the Encoder card's figures go out once a second as `recording.videoStatus`. Below 1 GB free (`RecordingCoordinatorOptions.VideoStopFloorBytes`) the video tracks stop with `video.diskFull` while the audio continues until its own 256 MB floor. Stop stops the audio, then the video (each file gets its `mfra` index, nothing else: it plays as written), and the manifest gets `videoTracks[]`, `hasVideo` and `videoPip[]`. Nothing in this path runs on an audio capture thread or takes a lock the audio path uses: the coordinator's calls come from the bridge and from the session's event dispatcher, and the video's own threads only queue their problems.
11. **Video stage** (`VideoStage`, `video`, §6): for recordings with video only. It joins a track's parts (`IVideoFiles.JoinAsync`: copied without decoding, or encoded again when an encoder change left parts that cannot be joined as they are), records the joined file and its hash in the manifest, and only then removes the parts; it computes the SHA-256 of every video file into `integrity` and writes History ("Video checked", with size, frame rate, length, size on disk, encoder and dropped frames). It is light and is listed second on the card but runs after the transcript stages (order 40), so it never holds a transcription back; finished, rows leave it out like `stored`. A failure keeps the recording on the processing card with the remedies `software` (encode the parts again) and `keepRaw` (keep the parts as written).
12. **Export** (`ExportPlanner` → `IVideoFiles.ComposeAsync` → `Mp4Composer`, processor only, so it never competes with a recording's capture on the card). "MP4" decodes the track to NV12, composes every output frame on the recording timeline at the track's frame rate (black before its first frame and after its end; the camera inset scaled into its corner, a quarter of the width, where `videoPip[]` had it at that time), and encodes H.264 at the track's bitrate through the sink writer (hardware transforms allowed; the software encoder when the graphics card's refuses system-memory pictures), with the mix as AAC 192 kb/s, written in time order. "Original container" copies the recorded H.264 samples untouched, shifted by the track's start (the MP4 sink keeps the offset), with the mix as AAC. One file is the screen with the inset; two files are each track at its own size, the mix with the screen. Progress is reported within the file; a cancelled or failed export leaves no file. Measured: 20 s of 1080p30 desktop in 8.8 s (71 frames/s) as MP4, 0.6 s as Original container (ENGINE-NOTES.md §M.8).
13. **Delete audio** (2.1, `AudioRemovalService`, the same pattern as the next item): `audio.remove` after the page's confirmation, and Settings › Storage and history › Delete audio tracks older than (`storage.deleteAudioOlderThanDays`: a day to five years, Never by default; swept by the same `VideoRetentionLoop` at launch, daily and when the age changes, never while recording or processing). The manifest records `audioRemoved` first (the tracks stay listed without hashes; `mix`, `peaks` and the audio hashes are cleared), then the audio files go (only audio files directly in `tracks/` and the mix and peaks at the top of the folder; leftover parts too; MP4 video never), then History says what was freed. Refused while the recording is recorded or saved or any of its stages is queued or running; afterwards every stage refuses to run again. The transcript, documents, attachments and video are untouched.
14. **Remove video, keep audio** (`VideoRemovalService`): `video.remove` after the page's confirmation, and Settings › Storage and history › Remove video older than (`storage.removeVideoOlderThanDays`, Never by default; swept at launch, daily and when the age changes, by the app's `VideoRetentionLoop`). The manifest records `videoRemoved` first and drops the video hashes, then the files go, then History says what was freed. Refused while the recording is recorded or saved, or while its video stage runs.
15. **Recovery** (`RecoveryService`): every part named by `recording.state.json` (or the manifest) is repaired with `IVideoFiles.Repair` (`VideoRecovery.Repair`: a torn last fragment cut off, nothing else touched) and its length and frames read back; the recovery dialog's item and the `recovered` History line count the video tracks intact.
16. **Playback.** Review plays `Project.videoTracks[].url` (`https://library.memento/<id>/tracks/screen.mp4`, the same virtual host as the mix; WebView2 serves the folder mapping with range requests, so the fragmented file seeks to the frame) with its `currentTime` slaved to the mix: video time = mix time − `startOffsetMs`.

## 6. Processing pipeline

A single **orchestrator** in Core runs stages per project: `Stored → Transcribe → Speakers → (Documents on demand) → Optimize` (the last only when a smaller storage format is chosen). 2.0 adds `Video` for recordings with video (§5.x): listed after Stored, run after the transcript stages. Each stage is an `IProcessingStage` with `RunAsync(project, progress, ct)`, is restartable, writes partial results, and appends to `history.jsonl` on start, progress milestones, completion and failure (with engine, model, device, duration).

- One GPU stage runs at a time. Transcription pauses when a recording is active and "pause when busy" is on, or when free space is low. The live transcript (§5.9) yields to both: it stops while a heavy stage runs and lets go of the card when another job asks for it; the full pass is unchanged by it.
- "PC is busy" (`ProcessingGate`): other programs above 85 % of the processor for 10 s pause a stage on the processor (one on the graphics card is exempt); it resumes after 15 s at 70 % or less. A busy pause that starts within 2 minutes of the previous one needs twice that pause's calm time (up to 5 minutes), so a load that comes back each time the stage starts gets room to finish. A stage that starts again writes its History start line only once.
- Resource probe: GPU presence and VRAM (via Vulkan or DXGI), CPU load, RAM. Free video memory is the smaller of the DXGI budget and the card minus what every process uses on it (PDH `\GPU Adapter Memory`); it matches `nvidia-smi` within about 20 MB whether the card is idle, held by another app or held by Memento's worker (ENGINE-NOTES §J). The separate card is chosen by the display driver's hybrid flags (D3DKMT `HybridDiscrete`/`HybridIntegrated`), else by vendor or ≥ 2 GB dedicated memory. The probe also names who holds the discrete card's memory (`\GPU Process Memory(*)`, summed by process for the card's LUID, top three, Memento's own processes as one "Memento", Ollama's server as "Ollama (llama-server.exe)", a runtime with the app that started it), cached for 4 s, never throwing; `engine.status`, `providers.list` and Settings say it in a §17 sentence when a model does not fit, and Settings' "Check again" (`engine.refresh`) reads it again (BRIDGE.md, "Graphics card memory"). The default model is the most accurate one that fits; a smaller model is offered, never applied silently. A model chosen in Settings is always the one in effect (the stage waits for it and says so); without a choice the model in effect is an installed one whenever any is installed (`TranscriptionModelChoice.EffectiveId`: the recommendation when installed, else the most accurate installed model, on the card when it fits and on the processor otherwise), so a PC with only Large v3 Turbo installed never waits for Small because another program holds the card's memory, and a damaged recommended model is set aside while an installed one transcribes (1.1.0).
- Failure keeps everything produced so far and offers the most specific remedy first (`Retry on CPU`, `Use the Medium model`).
- **Line times follow the sound** (after 1.2.0, ENGINE-NOTES.md §K). Whisper starts a line where the pause before it begins, often on whole seconds, and after a long silence can repeat one sentence for minutes. The worker therefore hears each 10-minute window packed: every sound region (10 ms edges; the bars follow each track's own noise floor and speech level, below) with 0.4 s around it, longer silences cut to 0.8 s, in chunks of at most 28 s cut between sounds, one engine call each (the language is detected on a window's first chunk and kept for the rest). Times are mapped back to the recording timeline (`PackedAudio`) and each line's start and end are moved to where sound starts and stops under it (`SpeechAligner`) before the seams are joined. Coverage gaps and the silent-track rule use the speech regions.
- **Every track at its own level** (after 2.0.0-beta.1, ENGINE-NOTES.md §Q). A quiet microphone beside loud system audio was skipped as "silent": its speech never cleared the fixed −40 dBFS speech bar. The tracks are transcribed separately (never as a mix), so nothing masked it; the bar did. `SpeechEnergy`'s bars are now relative to each track: speech above its noise floor (10th-percentile 100 ms frame) ×2 and sound ×1.6, and above floors that follow the track's speech level (`SpeechLevel`, an active level against its own noise floor in the spirit of ITU-T P.56): −40 / −50 dBFS for speech at −20 dBFS or louder (the §K bars, so line times are unchanged), 20 / 30 dB under the speech level for quieter tracks, never below −70 / −75 dBFS. The engines then hear each track's speech at one loudness: the worker normalizes each window (`LoudnessNormalizer`: active level to −20 dBFS, between −10 and +30 dB, soft limiter above 0.9; audio without speech keeps its level so silence and noise are never lifted on their own), the diarizer gets one gain per track, and the live draft normalizes each track per window before the sum (§5.9). Only copies of samples already on disk are changed; stored tracks are never touched and nothing runs on a capture thread.
- **History opens versions** (after 1.2.0): `history.links` infers from the files on disk which stored copy of the transcript or a document each History line produced (a copy is current from its `lastChange.at` until the write that kept it as a version; only the last line inside a copy opens it), so Review can show that copy read-only and restore it through the existing restore methods (BRIDGE.md, History links).
- **Speakers** (after 1.2.0). The worker diarizes each track with transcript lines by threshold only (it is never given a count), and returns each cluster's turns and voice embedding. The host (`SpeakerAssigner`) gives each line the cluster that overlaps it most on its track, then groups the clusters of all tracks into people: to the recording's own count (`details.whoSpoke`: the count, else the number of names), else Settings › Speakers › Expected speakers, voices with little speech set aside, the main ones joined most alike first until the count is met, then each little one joined to the main voice it sounds most like; never split. Without a count, main voices on one track that sound alike are joined, little ones join the main voice on their track they sound like (under 10 s of speech, always), and different tracks stay different people. Names a person gave carry over to the new speaker that took most of their lines, and Who spoke's names go to the rest in order of first appearance (`SpeakerNamer`). What the diarizer heard is kept in `voices.json`, with each cluster's lines, so identifying speakers again with a new count or names regroups at once, and Review's Reduce (`transcript.reduceSpeakers`) can merge the speakers whose current lines sound most alike. A pass over corrected lines keeps them as a transcript version first. Measurements: ENGINE-NOTES.md §L.
- **Known voices** (2.0, opt-in: Settings › Speakers › Remember speakers by voice, off by default). Naming a speaker in Review enrols its voice (the mix of the voices.json clusters of the lines it has now, from 10 s of voiced speech) under the name in `<library>/voices/known.json` (`KnownVoicesStore`, schema v1: per voice the newest 10 confirmations as unit vectors, the recordings that confirmed or declined it, and a Suggest flag; damaged entries dropped, a newer file refused, an unreadable one set aside). The signature is the mean of those confirmations. `VoiceMatcher` compares an unnamed speaker of a later recording with every known voice of the same voice model and suggests the best one at cosine 0.60 or more (0.50 for a Who spoke name or participant) and 0.10 more than any other known voice, one speaker per voice; nothing is applied until the user chooses Use name (rename, and the confirmation is added) or Not {name} (declined for that recording). Matching runs on demand (`voices.matches`) from voices.json, so the speakers stage needs no change. Each enrolment returns a change id that Undo reverts (an in-memory journal; forgetting a voice drops it from the journal). Deleting a recording removes its confirmations. Thresholds: ENGINE-NOTES.md §N.
- **Suggested chapters** (2.0). `ChapterSuggester` compares the subject words (as topics count them; the recording's topics weigh double) of the two minutes before and after each 30-second block edge; deeper-than-average dips become chapter starts (about one per ten minutes at most, three minutes apart), each moved to the nearby line after the longest pause or with a new speaker, titled by the phrase said most there and least elsewhere (a topic's label when it is about that topic). Deterministic, on demand (`annotations.suggestChapters`), no model; dismissed times are kept in annotations.json. An accepted suggestion is an ordinary chapter (origin `local`).

## 7. Transcript model

`transcript.json` (schema v1):

```jsonc
{
  "schemaVersion": 1,
  "language": "en", "languageDetected": true,
  "engine": { "name": "whisper.cpp", "model": "large-v3-turbo", "device": "GPU (Vulkan)", "version": "...", "durationMs": 123456 },
  "speakers": [ { "id": "spk1", "name": "Speaker 1", "renamed": false, "color": 1 } ],
  "segments": [
    { "id": "s0001", "start": 12.40, "end": 15.92, "track": "system", "speaker": "spk1", "speakerConfidence": 0.82,
      "text": "…", "confidence": 0.91,
      "words": [ { "w": "…", "s": 12.40, "e": 12.71, "c": 0.97 } ],
      "edited": { "at": "2026-10-06T10:12:00+01:00", "original": "…" } }
  ],
  "reviewed": false
}
```

Low-confidence threshold for the dotted underline: word confidence < 0.6 (settable). Uncertain speaker: `speakerConfidence < 0.7`. Renaming a speaker changes `speakers[].name` only; segments reference the id.

## 8. Documents, templates, styles

- **Template**: ordered rows, each with 1–3 modules; per module: type, instructions, length, linkToTranscript, **textSize** (`smaller` | `normal` | `larger`, applied as a factor of the style's base size in the preview, the viewer and the Word and PDF exports). Plus inputs checklist, provider, default style, output options.
- **Full transcript module**: a module whose content is the transcript itself (speaker, timestamp, text per segment, optional chapter headings), produced by the document composer from `transcript.json` with no AI involved. It is the only module that may be long; Word and PDF exports paginate it, Markdown emits it in full.
- **Style**: the Style editor settings (type, colour, structure, page). Built-ins Corporate, Minimal, Academic are presets.
- **Document**: a block model (`heading`, `paragraph`, `list`, `table`, `chips`, `labelValue`, `quote`, `timeline`) where any text run can carry a `t` timestamp reference (seconds) that resolves to a transcript moment. The viewer renders blocks to HTML with the style; DOCX and Markdown exporters consume the same blocks.
- **Generation**: the composer builds the payload from the ticked inputs only (never audio or video), shows it on request, sends it once, and expects structured output per module. The **grounding validator** checks every timestamp cites a real transcript time, that action items have an in-transcript source, and replaces unsupported claims with the spec's "not discussed / not reached / no owner was named" phrasing. The generation record stores the exact payload hash and, when "keep a record" is on, the payload itself.
- **Providers**: `IAiProvider` has three implementations. **Anthropic** and **OpenAI** are HTTP clients with keys in DPAPI. **Local** runs an on-device LLM through llama.cpp (LLamaSharp, MIT, with the Vulkan backend to match the transcription choice and the CPU backend as fallback) in the same out-of-process worker model as transcription, so a native failure cannot take down the app and VRAM is released after generation. Local models are GGUF files from the model manager catalog, chosen by free VRAM at run time (one GPU stage at a time; transcription and generation never run together); the catalog carries each model's license, size, context length, a verified chat-template id, and the minimum VRAM for the chosen quantisation. Defaults from the October 2026 spike (ENGINE-NOTES §H): **Qwen3.5-4B Q4_K_M** on GPUs with ≥ 3.3 GB free VRAM (16k context, f16 KV), **Ministral-3-3B-Instruct Q4_K_M** on CPU; both Apache-2.0. The worker reads free VRAM before choosing how many layers to offload, checks the context handle is valid after creation (an exhausted GPU returns a null handle instead of throwing), watches its own dedicated-vs-shared GPU memory and falls back to CPU or a smaller context when allocations spill to shared memory, warms up after load, serialises calls per context, and uses `DefaultSamplingPipeline` at temperature 0 with a GBNF grammar that allows natural whitespace. The provider exposes `ContextTokens` and a tokenizer so the pipeline below can budget chunks per provider. Local is positioned as private and good for a first draft with mandatory citations and review, not at parity with a cloud model.
- **Chunked, per-module generation with verification** (the same pipeline for every provider):
  1. **Segment**: the transcript is cut into chunks at chapter, topic and speaker-turn boundaries, each within the provider's chunk budget (Local: ~1,500 transcript tokens at 8k context, ~3k at 16k; cloud: larger). Timestamps are rendered as short segment ids to save tokens. Each chunk keeps its time range and speaker set.
  2. **Map**: for each module, each chunk is sent with that module's instructions and the inputs it needs (and nothing else), producing candidate items with citations (segment id plus the quoted words) as grammar-constrained JSON; the stop reason is checked so a truncated answer is retried with a smaller chunk rather than parsed.
  3. **Reduce in code, not with the model**: candidates are merged across chunks by citation overlap and text similarity, ordered by time, with a citation-repair step that moves a citation to the segment where its quote actually occurs; then they are written into the module's content shape within its length setting.
  4. **Verify**: a separate pass per module hands the model each claim with the exact transcript span it cites and asks only "does this span support the claim?", with names given exactly as they appear in the transcript and owner and due date checked as separate questions; unsupported claims are dropped or rewritten as "not discussed". With a cloud provider the cloud model performs this pass; the local model is not involved. The deterministic grounding validator then runs as the final gate for every provider.
  5. **Record**: the generation record lists chunks, prompts (hashes, or the text when "keep a record" is on), model, provider, timings, and the verification verdicts per claim, so "How this was made" and the History tab can show them.
  Every pass is cancellable, reports progress through `processing.progress`, and never blocks recording.
- **Decisions at M4d (October 2026).**
  - *Where it lives.* Core cannot reference Memento.AI or Memento.Documents (both reference Core), so the store, the pipeline, the provider registry and the M4 bridge methods are a project above them, `src/Memento.Generation`, added by the app with `AddMementoM4()`; Core keeps the bridge records, the names and codes, the worker records and `IDocumentExportSource` (the Export dialog's Documents row). Generation reports through `generation.progress`, not `processing.progress`.
  - *Who may send.* "Allow external AI services" governs the cloud providers only and is checked before anything is read or constructed; the local model runs whenever its model is installed and is the default when neither the template nor Settings names a provider. The share switches limit what a cloud provider receives; "ask before every send" holds cloud jobs only (the local model sends nothing). Providers are constructed only when a generation runs, the HTTP client on the first cloud generation.
  - *Local runs.* A whole generation is one worker process with one model load (`LocalAiProvider.OpenSessionAsync`, decided at the M4 integration): the job is started with `session: true`, each pass sends a `prompts` line and gets a `batch` line back, and `end` unloads it; Core's `WorkerClient.OpenAsync` keeps the graphics card for the whole session. Jobs that may use the graphics card share the transcription gate and the machine-wide GPU lock, and processor jobs are sent with `device: cpu` (the CPU build). The local model in effect is always an installed one when any is installed (`LocalModelChoice.EffectiveId`: the saved choice, else the hardware recommendation, else whichever is installed), so a PC with only Qwen3.5 4B or only Ministral 3 3B is never "not installed" (1.1.0). When Qwen3.5 4B (`runsOn: gpu`) has no room on the card, an installed Ministral 3 3B writes instead, otherwise Qwen runs on the processor (slower); `providers.list` names the model, where it runs and why, and Settings and the Builder show it; why includes the card's free memory and the programs holding the rest ("Ollama (llama-server.exe) is using 5.0 GB"), with the fix (`gpuNote`, after 1.1.0). Ministral 3 3B falls back to the processor. A spill while the model loads reloads it once at the profile's smallest context.
  - *Map.* One task per extraction: Decisions, Action items, Owner, Deadline and the Follow-up email share one decisions-and-actions pass (the spike's prompt); every summary-like module has its own pass with its instructions placed after the rules ("they never change the rules above"). Each request carries only the sections it needs (participants for owners, the agenda for coverage, details for summaries). Answers follow a JSON schema (a GBNF grammar with natural whitespace for the local model, item limits on); citations are a short line id plus the quoted words. The decisions-and-actions answer lists action items first (decisions first made the local model stop early); a summary-like section whose instructions aim at something the excerpt lacks writes about what it does say rather than nothing. A summary, executive summary, discussion summary or timeline that every chunk still answered with nothing is read once more as a plain summary under its title, without its own instructions (ENGINE-NOTES §I.2).
  - *Repair and reduce.* A quote that is not in the cited line (or running from it into the next) moves the citation to the nearest line that holds it, first in the same chunk; a quote that is nowhere even nearly (80% of its words) loses its citation. Duplicates merge when their words are similar (Jaccard ≥ 0.34, lightly stemmed) or they cite neighbouring lines with some overlap (≥ 0.2); the earliest is kept and the others are kept as alternates, tried in its place when it is not supported, so a wrong first copy cannot hide a right later one.
  - *Verify.* Each claim against two lines either side of its citation (an agenda item: from its line to six after); an action item's owner and due date are separate questions; names are the transcript's. Answers are graded supported / partly / not supported: "partly" keeps a summary point shortened to its supported part (only words of the claim or the excerpt), and for decisions, action items, owners, dates and agenda coverage it gets a second, plain yes/no vote over one more line either side. The local model answers numbered batches of up to 6 per module family without a reason per item; a cloud model answers batches of 25 with reasons. A summary-like module has only its length's worth of statements checked, then replacements for those that fail. An unanswered question is unchecked and the claim is dropped.
  - *Agenda coverage* also comes from code: each agenda item's words are matched against the transcript lines and the other passes' citations, and up to three matching lines per item become candidates for the verifier beside the model's own answer.
  - *Validator.* A claim is kept only with a resolvable citation and a supported verdict; a decision whose cited line parks, postpones, revisits or leaves it undecided is dropped; an owner stays only when named in the span or speaking the cited line or the next one, a due date only when its words are in the span; a quote must be the transcript's words; participants are the details' names and the named speakers. Lengths are applied after validation (short 3, medium 6, long 12 statements; commitments four times that), spread over the recording.
  - *Records and files.* The generation record (inputs sent, sizes, payload hash, the payload when "keep a record" is on, request hashes, timings, every claim with its verdict) is stored inside `documents/<id>.json`; versions are `versions/document.<id>.<utc-stamp>.json` with the transcript's rules; a template's "also export" copies go to `documents/exports/`. One History line per generation says exactly what was sent, where and the result.
  - *Live output.* The Builder's and viewer's **Show live output** sheet shows each pass's exact request and its reply as `generation.output` events (BRIDGE.md, Live output (M4)). The worker streams every answer while it decodes: the `llm` job's `progress` lines with phase `generating` carry the text decoded since the previous line, coalesced in the worker to the first piece and then at most one line every 40 ms or 8 pieces (`LocalTokenCoalescer`, on the decode thread: an append and a clock read per piece), and an `answered` line closes each prompt with its counts before the batch's `batch` line; grammar-constrained passes stream their raw tokens. On the host `RequestRunner` turns the session's progress into the job's `GenerationOutputFeed` (a request when the worker starts reading a prompt, tokens, the reply at `answered`; for a cloud provider the request when sent and the whole reply on arrival), and the pipeline adds the steps it does in code (segment, reduce, grounding). The feed only queues (an unbounded channel; the worker's reader never waits) and one reader publishes, holding token text to about ten events a second; `done` is sent before the job's final `generation.progress`. Nothing of it is logged or written: the UI keeps the exchange in memory until the Builder or viewer that shows it is left. Measured cost: ENGINE-NOTES §I.3.
  - *Preview what will be sent* (2.0). `generation.preview` builds, without sending or constructing a provider, the map requests exactly as a generation sends them (`GenerationPipeline.MapRequests`: the same tasks, chunks, prompts and titles; a test checks a generation then sends exactly these), plus an illustrative verify request (its claims come from the answers), each as its system prompt and user turn with sizes; every input of the checklist with its tick, whether it is in the payload and its size (`PayloadPreview`); what Settings' share switches hold back and what was left out or neutralised; the provider, model and "Ask before every send". The Builder shows it as a full-height read-only sheet (DESIGN.md §10.6) and copies it, or one request, through the host clipboard (`generation.copyPreview`).
- **Follow-up email** (2.0). The module reads two map families: the shared decisions-and-actions pass and a recap pass of its own (`points:<module id>`, at most 2, 3 or 5 statements by length), each claim verified and validated like every other. `FollowUpEmailWriter` writes it in code: "To" from the participants (details and named speakers), a subject from the title and date, then a greeting, an opening, the recap, Decisions, Action items with their owners and dates as spoken ("(no owner named)" otherwise) and a closing, the fixed sentences in the module's tone (neutral, warm, brief; `TemplateModule.Email`) and signed with its sign-off name. It is ordinary blocks (a label/value pair, paragraphs, lists), so DOCX, PDF and Markdown export it as its own section; `documents.copyModule` puts one module on the clipboard as plain text (`ModulePlainText`, no Markdown marks, no timestamps) and as HTML without the module heading or timestamps, so it pastes as an email.
  - *Measured* (RTX 3060 Laptop, Vulkan, Qwen3.5 4B Q4_K_M, 16k context, the spike's 20-minute synthetic meeting, Meeting minutes): 2 chunks, 75 requests, about 250–340 s end to end (map about 130–185 s, verify about 115–150 s, model loads about 11–51 s); decisions and action items recall 0.79, precision 1.00, no parked item as a decision; the verifier caught 6 of 6 planted false claims and accepted 12 of 14 true ones. With 1,500-token chunks recall stayed 0.79 (different misses) at twice the time, so the profile's 3,000 stays. At the M4 integration (ENGINE-NOTES §I.2): 28 requests and one model load, about 225 s on a shared card and 152 s on a nearly free one, recall 0.93 at precision 1.00, 14 of 14 true and 6 of 6 false fixed claims judged right, only the undiscussed agenda items "Not reached".

## 9. Reliability rules every builder follows

1. Recording never waits on anything else. No stage, dialog or network call may block the capture threads.
2. Never delete or overwrite user data except through the designed Delete flow. Finalized tracks are read-only.
3. All file writes are atomic; all JSON has `schemaVersion`.
4. Every failure is specific: name the thing, the time or amount, what is safe, then the fix. No bare "Something went wrong".
5. Nothing leaves the PC without an explicit user action, and audio/video never leave at all.
6. Unhandled exceptions flush recording checkpoints before the process exits, and write a crash report to the logs folder.
7. No personal data in the repository: no real names, emails, paths with user names, keys, or recordings. Test fixtures are synthetic.
8. Every bridge method, parser, exporter and the grounding validator has unit tests. Long-recording soak tests run before a release.
9. Tests never depend on the wall clock. CI runners (and a loaded PC) stall for tens of seconds, so:
   - **Wait for a signal or a condition, never for time.** Await the event, `TaskCompletionSource`, `WhenIdleAsync` or a polled condition, with `Patience.Ceiling` (30 s) as a ceiling that only fails a test when the signal never comes. No `Task.Delay` as a wait for work, and no event or job wait with a shorter limit.
   - **Assert on order, counts and readings taken around the action**, never "finished within N ms": bracket a time between two readings (`before ≤ mark ≤ after`), check that the i-th timer event comes no sooner than i intervals (less one 16 ms timer tick), and wait for the state the assertion needs (a checkpoint that already reports drift or has audio on every track), not for the clock to pass the point where it usually exists.
   - **Measure work, not time, for performance limits.** The parser hardening and fuzz tests count the processor cycles a parse used (`QueryThreadCycleTime`, `tests/Memento.Documents.Tests/Support/Work.cs`; the thread's own cycles plus every `ParseGuard` parse), with patterns run without their wall-clock match timeout inside a `RegexGuard.StartTally`, against budgets stated in cycles. A stall changes elapsed time, not cycles.
   - **Inject the delay instead of hoping for one.** Reproduce a starvation flake before fixing it: the synthetic capture's `DeliveryDelay` hands every packet over late, a probe delay in the product (removed before committing) widens a race, or the test host process is frozen in bursts. Keep the starved case as a test case when it is cheap (the recording-session tests run punctual and with packets 600 ms late).
   - **Put product timeouts under test on a clock the test moves.** A limit a test wants to see fire (or not fire) takes a `TimeProvider` (the worker watchdog's `WorkerClientOptions.Time`); the test uses `ManualTimers` and lets the limit pass once the code is waiting. A limit the test is not about gets `Patience.Ceiling` (the model download's connect timeout in its tests).
   - **Order races with signals.** To show a race is closed, hold one side on a `TaskCompletionSource` (a held index write, a file released in the first retry wait) rather than sleeping.
   - **Counted retries in the product.** Retry budgets that wait on other programs count the waits they ask for, not the clock (`AtomicReplace`, project delete, the recording drain on stop), so a starved machine still gets every try; a regex match stopped by its timeout after less work than a 1 GHz processor does in that time is retried as a stall (`RegexGuard`).

## 10. Accessibility and theming

- The WebView2 content follows the Windows app theme (`UISettings.ColorValuesChanged`) and switches live by toggling the `dark` class on the root; Settings can force light or dark.
